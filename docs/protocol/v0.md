# The APPricot wire protocol, version 0

**Status: Proposed draft of v0 (2026-09-20).** The normative message set is
[`wire.proto`](../../crates/appricot-proto/proto/appricot/v0/wire.proto); this document transcribes
it for review and never contradicts it — where the two disagree, `wire.proto` wins. The numbers
below await the X11 capture spike's measurements (milestone M1,
[roadmap.md](../roadmap.md)); anything the spike measures may still move before v0 is accepted.
The implementation landed on 2026-09-21 (both codecs, the streamer, the client and their tests,
green in CI): every statement this spec makes about code has been checked against it, and the
two decoders are proven byte-identical against the shared test vectors (§12).

The design rules this spec must satisfy are [README.md](README.md); §14 maps every rule to where
v0 satisfies it. The client's rules for server data are
[ADR-0003](../adr/0003-untrusted-server-client.md); the window model on the wire is the
Wayland-shaped model of [architecture.md §4](../architecture.md#4-the-window-model) and
[ADR-0004](../adr/0004-layers-window-model-and-first-backend.md); the encoding decision is
[ADR-0005](../adr/0005-wire-encoding-protobuf.md). All three ADRs are Proposed.

## 1. Encoding

The protocol is [Protocol Buffers](https://protobuf.dev/programming-guides/proto3/) proto3
(checked 2026-09-20), package `appricot.v0`, defined in the single file `wire.proto`.

- **Transport.** One WebSocket **binary** message per `Envelope`. Text frames never carry
  protocol messages (design rule 2).
- **Field order.** Both encoders emit fields in field-number order. A `encode(decode(x))` round
  trip is byte-identical. Protobuf does not promise deterministic field order in general
  ([proto3 language guide](https://protobuf.dev/programming-guides/proto3/), checked 2026-09-20);
  this protocol requires it, and the test vectors (§12) test it. Determinism is what lets a
  hand-written TypeScript codec mirror a generated Rust one.
- **Byte order.** Fixed-width fields are little-endian on the wire. Varints, zigzag and the
  length prefixes are whatever protobuf itself defines.
- **Unknown message.** An `Envelope` whose oneof names no field the receiver knows is a protocol
  violation: the receiver closes the connection without a reply. There is no skip-by-length in
  v0. This is the rule design rule 1 asked v0 to decide.
- **Unknown enum value.** An unknown enum value inside a known message is a protocol violation
  in v0, and the receiver closes the connection. Decided 2026-09-20, when the Rust codec
  landed: prost rejects unknown enum values on decode, and protobuf implementations disagree
  on preserving them, so v0 takes the strictest common rule rather than letting the two codecs
  diverge silently. New enum values ship only with a new protocol version, so a peer that
  meets one is talking to something it never agreed to. Both codecs enforce the closed sets
  in both directions: decode rejects, encode refuses to emit.

Every string on the wire is UTF-8, validated, and capped per field (§3). Strings are data for
display as text only; no field carries markup, a URL, or anything the client would execute or
navigate to ([ADR-0003](../adr/0003-untrusted-server-client.md) §1). Control characters are
**not** filtered on the wire in v0: both codecs validate UTF-8 and the byte caps and nothing
else, and the client's rendering path (`setTextOnly` / React children) puts a string into the
DOM as plain text, where control characters cannot execute anything. A future version may
tighten this; the decoders keep the rule identical so a tightening can be added to both at once.

## 2. Handshake and authentication

**Hello first, token inside it.** The first client message after the WebSocket opens is `Hello`
(C → S). It carries the credential for this leg — the per-session stream token — and negotiates
the version and the tile codecs. Nothing else is accepted before it. The token never travels in
a URL (design rule 8, [ADR-0004](../adr/0004-layers-window-model-and-first-backend.md): the
stream token must never reach the browser through anything the browser re-requests). A token
that does not match closes the connection with `Bye(BYE_AUTH_FAILED)`.

**Version.** `Hello.protocol_version` is the version the client wants. The server refuses a
version it does not support with `Bye(BYE_PROTOCOL_VERSION)`; it never guesses. The version both
speak is answered in `HelloReply.protocol_version`: the client's if supported, else the server's
best within the same major. The client closes on a version it did not ask for. See §13 for what
a version number means.

**Tile codec negotiation.** `Hello.codecs` lists the tile codec ids (§11) the client can decode,
best first, at most `MAX_CODECS_OFFERED`. **An empty offer means: only codec 1 (RAW)**, which
every peer must decode. `HelloReply.codecs` is the subset the server will actually send.

### Hello (C → S, must be first)

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `protocol_version` | `uint32` | — | The version the client wants. 0 in v0. |
| `client_name` | `string` | `MAX_CLIENT_NAME_BYTES` (64) | What the client is, for logs. Untrusted text. |
| `stream_token` | `bytes` | `MAX_TOKEN_BYTES` (256) | The per-session stream token. Opaque here; minting and checking are outside this protocol. Must match, or the connection closes with `Bye(BYE_AUTH_FAILED)`. |
| `codecs` | `repeated uint32` | `MAX_CODECS_OFFERED` (8) | Tile codec ids the client decodes, best first. Empty means RAW-only. |
| `resume_serial` | `optional uint32` | — | Present to reattach to a session that lost its socket: the `resume_serial` of the `HelloReply` being resumed (§7). |

### HelloReply (S → C)

The session exists from here on.

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `protocol_version` | `uint32` | — | The version both will speak (see above). |
| `session_id` | `string` | `MAX_SESSION_ID_BYTES` (64) | Identifies the session in logs and support. Untrusted text for display. |
| `max_frame_credits` | `uint32` | — | The frame-credit limit the server will honour per surface (`MAX_FRAME_CREDITS`, §6). |
| `codecs` | `repeated uint32` | — | The codecs the server will actually send, a subset of the client's offer. |
| `resumed` | `bool` | — | True when this connection resumed the session named by `Hello.resume_serial`. False, and the session state starts fresh, when there was nothing (left) to resume. |
| `resume_serial` | `optional uint32` | — | Present when resuming is possible later: the serial to present in a future `Hello.resume_serial` (§7). |
| `resume_grace_ms` | `optional uint32` | — | How long the session survives a lost socket (`RESUME_GRACE_MS`, §7). |

## 3. The limits table

Design rule 3: every length, count and dimension has a maximum. The table's authoritative home
is the comment block in
[`wire.proto`](../../crates/appricot-proto/proto/appricot/v0/wire.proto); it is mirrored in
`crates/appricot-proto/src/limits.rs` and in `packages/client/src/limits.ts`, and transcribed
here.

| Name | Value | What it caps |
|---|---|---|
| `MAX_MESSAGE_BYTES` | 16,777,216 | One WebSocket binary message (both directions). |
| `MAX_FRAME_CREDITS` | 4 | Frames sent and not yet acked, per surface. |
| `MAX_SURFACES` | 64 | Living surfaces in one session. |
| `MAX_POPUPS_PER_PARENT` | 16 | Living popups of one parent surface. |
| `MAX_SURFACE_WIDTH` | 1920 | Pixels. |
| `MAX_SURFACE_HEIGHT` | 1200 | Pixels. |
| `MAX_TILE_WIDTH` | 256 | Pixels. |
| `MAX_TILE_HEIGHT` | 256 | Pixels. |
| `MAX_TILES_PER_FRAME` | 48 | Tiles in one `Frame`. |
| `MAX_TILE_BYTES` | 262,144 | Bytes of one tile payload (256*256*4 raw). |
| `MAX_TITLE_BYTES` | 512 | `SurfaceNew`/`SurfaceMetadata` title. |
| `MAX_APP_ID_BYTES` | 256 | `SurfaceNew`/`SurfaceMetadata` app id. |
| `MAX_CLIENT_NAME_BYTES` | 64 | `Hello.client_name`. |
| `MAX_SESSION_ID_BYTES` | 64 | `HelloReply.session_id`. |
| `MAX_BYE_TEXT_BYTES` | 256 | `Bye.text`. |
| `MAX_ERROR_TEXT_BYTES` | 1024 | `ServerError.text`. |
| `MAX_TOKEN_BYTES` | 256 | `Hello.stream_token`. |
| `MAX_KEY_CODE_BYTES` | 16 | `Key.code` (physical key name, e.g. "KeyA"). |
| `MAX_CODECS_OFFERED` | 8 | Entries in `Hello.codecs`. |
| `MAX_CLIPBOARD_BYTES` | 65536 | `ClipboardSet.text`, in UTF-8 bytes. |
| `MAX_CURSOR_WIDTH` | 128 | Pixels. |
| `MAX_CURSOR_HEIGHT` | 128 | Pixels. |
| `MAX_CURSOR_BYTES` | 65536 | Bytes of `CursorImage.argb_premultiplied`. |
| `RESUME_GRACE_MS` | 10000 | How long a session outlives its socket (§7). |

**Enforcement.** Both peers enforce every row **before** allocating or looping: a decoder reads
a length, checks it against the table, and only then allocates, copies or iterates. A violation
closes the connection with `Bye(BYE_LIMIT_VIOLATION)`. The limits are a property of version 0
(§13): the values may be tuned only as §13 allows, and any peer that meets this table meets v0.

`MAX_MESSAGE_BYTES` is enforced twice on the receiving streamer, by design: the WebSocket
implementation's own frame cap rejects an oversized single frame before the protocol decoder
is reached (measured 2026-09-21: the connection dies on the frame header, so the decoder-level
refusal is the second line of defence), and the protocol decoder rejects the length again for
anything that arrives assembled. Either layer refusing closes the connection; a client can
observe the close without learning which layer fired.

### 4.2 Surfaces

**SurfaceNew (S → C).** A window appeared and becomes a surface the host shows.

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `surface_id` | `uint32` | — | Unique within the session, never reused. |
| `role` | `Role` | — | Toplevel or popup, set once. |
| `parent_id` | `optional uint32` | — | A dialog's toplevel parent, or a popup's parent surface. Absent for a plain toplevel. |
| `size` | `Size` | `MAX_SURFACE_WIDTH`/`HEIGHT` | The size the surface starts with. The server cuts every size to the caps: a larger window is streamed as its top-left part. |
| `title` | `string` | `MAX_TITLE_BYTES` (512) | Untrusted text. |
| `app_id` | `string` | `MAX_APP_ID_BYTES` (256) | Untrusted text. |
| `positioner` | `optional Positioner` | — | Present for `ROLE_POPUP`: how the popup is placed inside its parent. |
| `scale_120ths` | `uint32` | — | Device pixels per logical pixel in 120ths: 120 is 1x, 240 is 2x. Never zero. |

**SurfaceGone (S → C).** The surface is gone; its id is never reused.

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `surface_id` | `uint32` | — | Which surface went. |
| `reason` | `SurfaceGoneReason` | — | `GONE_APP_CLOSED = 0` (the app closed the window itself), `GONE_PARENT_GONE = 1` (its parent went first; popups do not outlive parents), `GONE_SESSION_END = 2` (the session is ending and everything goes with it; the landed streamer never sends it, because a session ends with `Bye`). |

**SurfaceMetadata (S → C).** Title, app id or scale changed. Absent fields are unchanged.

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `surface_id` | `uint32` | — | Which surface changed. |
| `title` | `optional string` | `MAX_TITLE_BYTES` | Untrusted text. |
| `app_id` | `optional string` | `MAX_APP_ID_BYTES` | Untrusted text. |
| `scale_120ths` | `optional uint32` | — | New scale, in 120ths. Never zero. |

**FocusAsk (S → C).** The app asked for the keyboard focus (X11 `_NET_ACTIVE_WINDOW`). The host
decides; nothing moves unless the host answers with `FocusNotify`. The server never sets focus by
itself ([ADR-0003](../adr/0003-untrusted-server-client.md) §5: a server request to focus is an
event, the host decides).

| Field | Type | Semantics |
|---|---|---|
| `surface_id` | `uint32` | Which surface asked. |

**ResizeAsk (S → C).** The app asked to resize itself (X11 ConfigureRequest on its own window).
The host decides; it answers with `Configure` if it agrees. A `ResizeAsk` changes nothing by
itself: the surface keeps its size until a configure is applied.

| Field | Type | Semantics |
|---|---|---|
| `surface_id` | `uint32` | Which surface asked. |
| `size` | `Size` | The size the app wants. |

**Configure (C → S).** The host proposes a size. The serial names this proposal; the server
answers once the app has taken a size, with `ConfigureAck` carrying the same serial.

Proposals may overlap, as they do while the host resizes a window live. The server keeps the
ones not yet answered, oldest first, up to 16 per surface; past that the oldest is dropped. When
the app takes a size, the server acks the newest waiting proposal of exactly that size, which
answers every older one too. When no waiting proposal has that size (the app clamped), it acks
the newest. A proposal of the size the surface already has, with nothing waiting, changes
nothing and is acked at once. Proposals still waiting when the socket dies are forgotten: a
resume re-announces the size the surface has (§7).

| Field | Type | Semantics |
|---|---|---|
| `surface_id` | `uint32` | Which surface. |
| `serial` | `uint32` | Names this proposal. Never 0: 0 marks a size change no configure asked for (below). |
| `size` | `Size` | The proposed size. |

**ConfigureAck (S → C).** The surface has a new size, and this is it. The host sizes its chrome
to it, and the client's bounds for the surface's tiles follow it. The server sends it before any
`Frame` whose tiles use the new size.

- **A nonzero serial** answers the configure it names, and every older one of that surface: the
  app applied it, or clamped it to its own limits. The size is the size the app really took.
- **Serial 0** answers no configure. The app changed the size on its own, with no proposal
  waiting: a popup that grows itself, say. It is a fact, not a request; a host that wants
  another size answers with a `Configure`.

| Field | Type | Semantics |
|---|---|---|
| `surface_id` | `uint32` | Which surface. |
| `serial` | `uint32` | The newest configure being acked, or 0 for a size the app took on its own. |
| `size` | `Size` | The size the app really took. |

### 4.3 Frames

**Frame (S → C).** The changed pixels of one surface since the previous acknowledged frame.
`sequence` is per-surface, starts at 1 and rises by one. With `full_redraw` set the client drops
every tile it holds for the surface and this frame's tiles cover the whole surface.

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `surface_id` | `uint32` | — | Which surface. |
| `sequence` | `uint32` | — | Per-surface, starts at 1, rises by one. |
| `full_redraw` | `bool` | — | Drop all held tiles; this frame covers the whole surface. |
| `tiles` | `repeated Tile` | `MAX_TILES_PER_FRAME` (48) | The changed pieces, in surface coordinates. |

**Tile** (inside `Frame`):

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `rect` | `Rect` | `MAX_TILE_WIDTH`/`HEIGHT` (256) | In surface coordinates, before scale; the decoder scales to the host's device pixels. |
| `codec` | `uint32` | — | A tile codec id from §11. 0 is a protocol violation. |
| `data` | `bytes` | `MAX_TILE_BYTES` (262,144) | The encoded pixels. |

**FrameAck (C → S).** The client has **drawn** this frame; the server frees the credit. An ack
for a sequence it does not hold is ignored, never fatal.

| Field | Type | Semantics |
|---|---|---|
| `surface_id` | `uint32` | Which surface. |
| `sequence` | `uint32` | The frame that was drawn. |

**CursorImage (S → C).** The cursor image changed. `serial` rises monotonically; the client drops
a cursor image whose serial it has already drawn. The server counts serials per session, one per
image it sends, even an image the app showed before: toolkits return to cached cursors, and a
serial that named the cursor object would make the client drop the arrow it saw first. An image
identical to the one just sent is not sent again.

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `serial` | `uint32` | — | Monotonic; a stale serial is dropped. |
| `width`, `height` | `uint32` | `MAX_CURSOR_WIDTH`/`HEIGHT` (128) | Pixels. |
| `hotspot_x`, `hotspot_y` | `uint32` | — | The hotspot inside the image. |
| `argb_premultiplied` | `bytes` | `MAX_CURSOR_BYTES` (65,536) | `width * height * 4` bytes, row-major from the top, each pixel ARGB with premultiplied alpha, 8 bits per channel. |

**CursorGone (S → C).** The cursor left the visible set; draw the host's own cursor again. No
fields.

## 5. Lifecycle

**Bye (either direction).** Sent before closing the socket. After a `Bye` the socket closes;
nothing follows.

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `reason` | `ByeReason` | — | Why (below). |
| `text` | `string` | `MAX_BYE_TEXT_BYTES` (256) | Untrusted text for display. |

`ByeReason` values: `BYE_PEER_CLOSED = 0` (the peer closed on its own initiative), and the
failures `BYE_PROTOCOL_VERSION = 0x100`, `BYE_LIMIT_VIOLATION = 0x101`, `BYE_AUTH_FAILED = 0x102`,
`BYE_PROTOCOL_VIOLATION = 0x103` (a message the peer could not decode, or in an order it
forbids), `BYE_SESSION_GONE = 0x104`, `BYE_SERVER_SHUTDOWN = 0x105`.

**ServerError (S → C).** Sent immediately before a close **the client caused**. Nothing follows
it either.

| Field | Type | Cap | Semantics |
|---|---|---|---|
| `code` | `uint32` | — | A stable code number. v0 codes: 1 limit violation, 2 reserved (unused in v0 — with a oneof envelope an unknown message IS a decode failure), 3 bad order, 4 decode failure, 5 internal error. |
| `text` | `string` | `MAX_ERROR_TEXT_BYTES` (1024) | Untrusted text for display. |

Order rules v0 forbids (violation closes, `BYE_PROTOCOL_VIOLATION`): anything before `Hello`;
a `Hello` after the handshake; a message from the wrong direction; an ack for a serial or
sequence that names nothing is **ignored** rather than fatal (§4.3) — the fatal orders are the
impossible ones, not the stale ones.

## 6. Flow control

Design rule 5. Frames are paced by the client's acks, never by a timer.

- **Credits.** The server holds at most `MAX_FRAME_CREDITS` (4) frames in flight per surface —
  sent and not yet acked. `HelloReply.max_frame_credits` states the number the server honours.
- **Sequence numbers.** Each `Frame.sequence` is per-surface, starts at 1 and rises by one. The
  client can detect gaps; a gap is a protocol violation on the server's part.
- **Ack after draw.** `FrameAck` means the client has *drawn* the frame, not merely received it.
  The server frees the credit only then.
- **Coalescing.** While no credit is free, the server coalesces damage into the dirty region and
  sends fewer, larger frames. A slow client makes the server coalesce, not queue.
- **Nothing on a timer.** An idle window sends nothing. No keepalive, no heartbeat, no refresh
  tick exists in v0. The one sanctioned timer in the whole protocol is the resume grace of §7 —
  and it ends a dead session, it does not send anything.

## 7. Reattachment

Design rule 11. A dropped socket does not end the session.

- **Grace window.** When the socket dies, the server keeps the session for `RESUME_GRACE_MS`
  (10,000 ms), the value `HelloReply.resume_grace_ms` carries. This is the session's lifetime
  after the transport; inside it, resuming is possible.
- **Resume.** The client reconnects and sends `Hello` with `resume_serial` — the value of
  `resume_serial` in the session's first `HelloReply`. The server answers
  `HelloReply.resumed = true` and resynchronises:
  - the **whole window set** first: every living surface re-sent as `SurfaceNew`, in creation
    order, as it stands (size, title, app id, scale, role, parent, and a popup's positioner
    with the size the popup has now);
  - then **exactly one cursor message**: `CursorImage` with the current image under a new
    serial, or `CursorGone` when the session knows no cursor. The re-announcement ends at the
    first message that is not `SurfaceNew`, so a client drops every surface it held that was
    not re-announced, and updates, never removes and re-adds, one that was;
  - **one full frame per living surface**: a `Frame` with `full_redraw` set and the surface's
    next sequence number — the client drops every tile it holds and repaints from this frame.
  No damage is replayed; what the client missed is inside the full redraw.
- **After the grace.** The session is gone: window set, surfaces, sequence numbers, credits,
  held keys, and — because a v0 streamer serves one session per process — the backend with it.
  What a reconnect then meets, measured on the landed streamer (2026-09-21): the WebSocket
  upgrade is refused over HTTP (the readiness endpoint reads red once the display session is
  torn down), so no `Hello` is read at all. **Inside** the grace window the replacement rule
  below holds: an authenticated `Hello` whose `resume_serial` names nothing replaces the parked
  session with a fresh one (`HelloReply.resumed = false`), and `Bye(BYE_SESSION_GONE)` is
  answered only while a session is parked whose backend died. A client that wants a new session
  from a live streamer simply sends `Hello` without `resume_serial`.

- **A refused handshake claims nothing.** The session belongs to an *authenticated* `Hello`, not
  to the WebSocket upgrade. A first message the server refuses — a bad token, an unsupported
  version, a text frame where a binary one is required — answers the `Bye` the spec names and
  releases the slot, so the next upgrade, or a retry with the right token, is served normally.
  Measured on the landed streamer (2026-09-21): before this rule held, the upgrade itself
  claimed the session, so a single mistyped token left the process refusing every later upgrade
  with `503` until it was restarted.

## 8. Keyboard mapping (client side)

Keysym first: the keysym is the authoritative meaning of the key event; the physical code rides
along for keys that carry no character and for shortcuts.

- **Single-character keys.** A key event whose `key` is one character maps to a keysym by
  codepoint:
  - Latin-1 (U+0020 to U+00FF) is sent as the codepoint itself — the X11 Latin-1 keysyms carry
    the same numbers as the characters;
  - the Greek block (U+0370 to U+03FF) is likewise sent as the bare codepoint;
  - every other character uses X11's Unicode keysym encoding, codepoint + 0x01000000: any
    Unicode character U+0100 to U+10FFFF "can be represented by a keysym value in the range
    0x01000100 to 0x0110FFFF"
    ([xkbcommon keysym docs](https://xkbcommon.org/doc/current/group__keysyms.html),
    checked 2026-09-20).
- **The Greek spelling is a convention of this protocol.** X11's *named* Greek keysyms live at
  0x07xx — `XK_Greek_alpha` is 0x07e1 for U+03B1
  ([keysymdef.h](https://gitlab.freedesktop.org/xorg/proto/xorgproto/-/raw/master/include/X11/keysymdef.h),
  checked 2026-09-20) — so a bare 0x0370-0x03FF value is not one of them. The backend maps that
  range onto the 0x07xx keysyms before its keymap lookup; a keysym that matches no keycode in the
  current keymap fails delivery with a named error and is logged, never fatal to the session — on
  the default US layout of a bare Xvfb that is the fate of Greek until a Greek layout is
  configured (measured by the implementation, 2026-09-21; the spike owns the on-device answer).
  Greek matters because M2 requires US and Greek layouts, AltGr and dead keys
  ([roadmap.md](../roadmap.md)).
- **Named keys.** Non-character keys (Enter, Tab, arrows, F-keys, modifiers) map from
  `KeyboardEvent.code` to a keysym through a named-key table in the client's key-mapping module
  (`keysymFor` in `packages/client/src/input.ts`, landed 2026-09-21).
  The table is client state, not wire state; the wire carries only its result.
- **Physical code.** `Key.code` is the browser's `KeyboardEvent.code`, which "contains
  information about the key event that can be used to identify the physical key being pressed"
  and does not vary with the user's locale
  ([UI Events KeyboardEvent code Values](https://www.w3.org/TR/uievents-code/), W3C
  Recommendation, checked 2026-09-20). ASCII, non-empty, at most `MAX_KEY_CODE_BYTES` (16).
- **Modifier bitmask.** `Key.modifiers` bits: 1 shift, 2 lock (caps), 4 control, 8 alt, 16 meta,
  32 altgr.
- **No stuck keys.** When the host page loses focus the client sends `BlurRelease`, and the
  server releases every key and button it holds (§4.4,
  [ADR-0003](../adr/0003-untrusted-server-client.md) §6).

## 9. Pointer mapping

- **Buttons.** `PointerButton.button` uses the X button numbers: **1 left, 2 middle, 3 right**.
- **Wheel.** `PointerAxis` carries **discrete wheel steps** — `steps_y` negative is up, positive
  is down; `steps_x` negative is left, positive is right. v0 has no smooth scrolling, no pixel
  deltas, no momentum.
- **Coordinates.** All pointer coordinates are surface-local (design rule 7): (0, 0) is the
  surface's top-left, `x` grows right, `y` grows down. Never a global screen position — a server
  cannot aim input outside its windows. Coordinates may sit just outside a popup's edge while a
  drag crosses it; the backend clamps.

## 10. Popup placement

A `ROLE_POPUP` surface arrives with a `Positioner` (§4.1): an anchor rectangle in the parent's
coordinates, the anchor point on it, the gravity the popup grows towards, a final offset, and
the popup's size — xdg_positioner in miniature ([xdg-shell](https://wayland.app/protocols/xdg-shell),
checked 2026-09-20). The host places the popup from the positioner, then **clamps** the placed
rectangle to its parent's content box plus a small fixed margin, whatever the positioner says;
a popup whose parent is gone is dropped ([ADR-0003](../adr/0003-untrusted-server-client.md) §5).
The server cannot place a popup outside its parent's box by asking nicely; the client does not
obey, it clamps.

## 11. Tile codecs

Codec ids are stable on the wire for the life of version 0. **0 is never a codec**: a `Tile`
with codec 0 is a protocol violation.

| Id | Codec | Layout |
|---|---|---|
| 1 | **RAW** | Uncompressed pixels, row-major, top to bottom, 4 bytes per pixel in the order blue, green, red, unused (the X11 32-bit ZPixmap byte order). No stride padding: exactly `width * 4` bytes per row. Every peer must decode it. |
| 2 | **QOI** | The QOI image format ([qoiformat.org](https://qoiformat.org), checked 2026-09-20). The QOI header names 3- or 4-channel data; a 3-channel tile decodes to opaque pixels. |

Licence note. The QOI specification page releases the format text as public domain under CC0
([qoiformat.org](https://qoiformat.org), checked 2026-09-20) and the reference implementation is
MIT ([phoboslab/qoi](https://github.com/phoboslab/qoi), checked 2026-09-20). APPricot writes its
own encoder and decoder from the published specification on both sides, so no third-party code
enters the dependency graph ([ADR-0002](../adr/0002-licence.md)).

## 12. Test vectors

Design rule 10: the Rust codec generates the test vectors; the TypeScript codec must pass them;
both decoders are fuzzed.

- **Path.** `crates/appricot-proto/testdata/vectors.json` *(landing with the codecs; to be
  confirmed by the implementation report)*.
- **Who generates, who consumes.** The Rust codec (`crates/appricot-proto`) generates one vector
  per message plus edge cases at the limits. The TypeScript codec
  (`packages/client/src/protocol.ts`) must decode every vector byte-exactly and re-encode it to
  the same bytes.
- **The byte-identity rule.** Because both encoders emit fields in field-number order (§1), an
  `encode(decode(x))` round trip is byte-identical on both sides. The vectors pin the exact
  bytes, so the hand-written TypeScript codec cannot drift from the generated Rust one; this is
  the gate that makes the two-codec decision of [ADR-0005](../adr/0005-wire-encoding-protobuf.md)
  safe.

## 13. Versioning

- **Major-only.** The wire carries one number, the major. v0 peers say `0`. There are no minor
  numbers on the wire; within a major, changes only add (design rule 1).
- **Additive-only within a major.** Safe without a bump: a new field with a fresh field number
  in an existing message, or a raised limit. A new **enum value is NOT additive here**: both
  codecs reject unknown enum values (§1), so a new one closes an older peer's connection and
  belongs to a new protocol version.
- **New envelope messages need care.** An older receiver treats an unknown envelope oneof as a
  violation and closes (§1). A new message therefore ships only when every peer of that major
  deployed beside it understands it — or after a negotiation that proves the peer does. v0 has
  no such negotiation; adding one would itself be the first such message problem.
- **What forces v1.** Anything a v0 decoder cannot handle: renumbering or removing a field,
  changing a field's type or meaning, re-using an id, new semantics for an old value, or
  lowering a limit below what v0 peers may send.

## 14. How v0 satisfies the design rules

[README.md](README.md) lists eleven rules. Where each is satisfied:

| # | Rule | Where in v0 |
|---|---|---|
| 1 | Versioned | §2 (refuse and close, never guess), §13; unknown message = close, decided in §1. |
| 2 | Binary WebSocket frames | §1: one `Envelope` per binary message, little-endian fixed widths, no self-describing encoding. |
| 3 | Bounded | §3: the limits table, checked before allocating or looping; violation closes. |
| 4 | Text-only strings | §1 and every string field: UTF-8, capped, untrusted text ([ADR-0003](../adr/0003-untrusted-server-client.md)). |
| 5 | Flow control | §6: credits, sequences, ack after draw, coalescing, nothing on a timer. |
| 6 | The host decides | §4.2: `Configure`/`ConfigureAck` with a serial; `FocusAsk` asks, only `FocusNotify` moves focus. |
| 7 | Surface-local coordinates | §9 pointer coordinates, §10 popup placement, clamped ([ADR-0003](../adr/0003-untrusted-server-client.md) §5). |
| 8 | Authentication first | §2: `Hello` carries the token, nothing else accepted before it, token never in a URL. |
| 9 | No I/O in the codec | §12: the codec turns bytes into typed messages and back; no message in the set requires a clock, a socket or a retry — the one timer (§7) belongs to the session, not the codec. |
| 10 | Test vectors are shared | §12: Rust generates, TypeScript passes, both fuzzed. |
| 11 | A dropped transport is not a dead session | §7: grace window, `resume_serial`, resync by window set plus full redraw. |

## 15. Example sequences

### Connect, first window, configure, frame

```
 client                                         streamer
   | ---- WebSocket connect (binary only) --------> |
   | ---- Envelope{ hello } --------------------->  |   version 0, token, codecs [2, 1]
   | <---- Envelope{ hello_reply } --------------   |   version 0, session_id, credits 4,
   |                                                |   codecs [1], resume_serial 12
   | <---- Envelope{ surface_new } -------------    |   id 1, toplevel, size, title
   |     host creates its chrome, attaches canvas   |
   | ---- Envelope{ configure } ----------------->  |   serial 7, size
   | <---- Envelope{ configure_ack } ------------    |   serial 7, the size the app took
   | <---- Envelope{ frame } -------------------    |   id 1, sequence 1, full_redraw, tiles
   |     client draws the tiles, then:              |
   | ---- Envelope{ frame_ack } ----------------->  |   sequence 1
```

### A popup

```
 client                                         streamer
   | <---- Envelope{ surface_new } -------------    |   id 4, popup, parent 1, positioner
   |     host places it, clamped to parent+margin   |
   | <---- Envelope{ frame } -------------------    |   id 4, sequence 1, full_redraw
   | ---- Envelope{ frame_ack } ----------------->  |
   | ---- Envelope{ pointer_move } ------------->   |   id 4, surface-local x, y
   | <---- Envelope{ surface_gone } -------------   |   id 4, app closed the menu
```

### Reattach after a drop

```
 client                                         streamer
   | ~~~~ socket drops ~~~~~                        |   resume grace (10 s) starts
   | ---- WebSocket connect ----------------------> |
   | ---- Envelope{ hello } --------------------->  |   resume_serial 12
   | <---- Envelope{ hello_reply } --------------   |   resumed = true
   | <---- Envelope{ surface_new } for each window  |   the whole window set
   | <---- Envelope{ frame } per living surface     |   full_redraw, next sequence
   | ---- Envelope{ frame_ack } ----------------->  |
```
