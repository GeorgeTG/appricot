# The M2 real-browser pass on desktop browsers, 2026-09-28

The browser half of M2's tail, recorded. **M2 stays open**: the other half is the pilot application
on a real device, and Safari is not run here. The rig is [README.md](README.md); each run's raw
log is committed next to this page, and the screenshots under this directory are the pictures that
claim is checked against.

**What the pass ran against.** The demo host page from the `demo` recipe, one session per run
(the streamer serves one session per process, so a browser that closes ends the recipe's run). The
display held two X clients from the dev image — `xlogo` and `xev` — plus the repository's own
stand-in application, `appricot-spike fake-app`, whose toplevel scrolls, whose override-redirect
popup maps for one second, and whose transient dialog follows it. **None of them is the pilot
application**: what this pass streamed is a stand-in app and two X utilities, and the window set
below is exactly that.

### The window set and the popups

Chromium opened `session session-1` (`#status = "open"`) onto two host windows for the two X
toplevels: `XLogo` at 100x100 and `XInputProbe` at 178x178, each on a canvas of the app's own size
([chromium-session-open.png](chromium-session-open.png)). When the stand-in app started, its
toplevel and its transient dialog arrived as two more host windows, and its override-redirect popup
arrived inside its parent: the parent's content box was `(81,166) 640x400` and the popup's box
`(121,226) 160x120` — 40 px right and 60 px below the parent's origin, which is where its
positioner asked for it, inside the parent's box, and the layer clips at its own edges
([chromium-popup-in-parent.png](chromium-popup-in-parent.png)). The override-redirect popup lives
one second: it was measured on the frame it mapped.

The clamp itself was not driven to its edge: the pass then moved the popup's X window to a corner
outside its parent (`xdotool windowmove … 1000 620`) and the host's popup box did not move — same
numbers, before and after. So the host keeps the popup where its parent puts it; the case where a
positioner asks for a place outside the parent-plus-margin box is the hostile fixture's, and that
is a CI test.

### Focus, drag, resize, minimise, close

- **Focus**: clicking a window's title bar left it `class = "window focused"` with
  `document.activeElement` on that window's canvas, which is where the key listener lives.
- **Drag**: the title bar moved the host window by exactly the drag, `(24,81) → (164,191)`.
- **Resize**: the grip dragged by +90 x, +70 y turned the app's canvas from 100x100 into 190x170
  ([chromium-window-resized.png](chromium-window-resized.png)) — the size came back through the
  app, not from the drag itself.
- **Minimise and restore**: the window took `class = "window minimized"`, the toolbar strip grew a
  restore button labelled with the window's own title, and the restore brought it back focused.
- **Close**: the XLogo window's close button sent the close request, and the window left the
  session (2 windows → 1, `#windows-count = "1 window"`) because `xlogo` exits on
  `WM_DELETE_WINDOW`. The stand-in app's window is not closable this way — it never lists the
  protocol, and the backend does not kill a window that never asked to be closed.

### Input: US, Greek, AltGr and dead keys

The observer is the stand-in app itself: its key reports recompute each keysym from the server's
keymap and refetch that keymap on every change, which is the same reading the backend's own tests
take. From `input-probe.mjs` on the same rig, the app received:

```
a 0x61  Shift_L 0xffe1  A 0x41  1 0x31  Return 0xff0d  Left 0xff51
Greek alpha, on the physical KeyA:   keycode 248, keysym 0x7e1   (a spare keycode, rebound)
EuroSign, AltGr held (ISO_Level3_Shift, state 0x80): keycode 14, keysym 0x20ac
dead acute then alpha:               keycode 248 keysym 0xfe51, then keycode 230 keysym 0x7e1
```

So the character the browser typed is the keysym the app was given: α as Greek_alpha, € as
EuroSign, and ά as the layout's own dead-acute-then-alpha sequence. The client sent every one of
them as a `Key` envelope (the pass counted them on the wire), and the streamer reached each one —
including the ones the keymap cannot reach in its first two columns, which it delivers by holding
the level-3 key or by rebinding a spare keycode for the press.

Two honest qualifications. The display had `setxkbmap us,gr` set before the streamer started; on
the recipe's default `us` display, a Greek character is refused by the backend by design — a keysym
the keymap does not hold is never pressed as another key, the streamer logs
`input delivery failed … what="key"`, and nothing reaches the app (measured: that is what the
earlier runs of this pass saw, and it is correct behaviour, not a defect). And the release of a
rebound key reads as `NoSymbol` in the log above, because the bind is already restored when the
observer reads the row: what matters is the press.

Firefox typed the US set (a, A, 1, Enter, ArrowLeft all arrived) but **could not be given the
other characters**: Playwright's Firefox refuses a key name outside its layout table
(`keyboard.down: Unknown key: "α"`), and the pass records that as not run rather than passing it.
The mapping across `us`, `gr` and `us,gr` is the backend's own test
(`crates/appricot-x11/tests/keysym_groups.rs`), which is CI.

### The clipboard, both directions

Chromium, app to host: another X client took the `CLIPBOARD` selection, the streamer fetched the
text, and the page showed the copy button enabled while the user's clipboard still held a sentinel
written for the test. The click — a real gesture — put `APPricot app-side clipboard text` on the
clipboard, and `#status` said `copied to your clipboard`. So nothing was written before the
gesture and the gesture wrote it. (Firefox did the same, through its own clipboard API.)

Chromium, host to app: with the paste toggle on, text was put on the browser's clipboard and
`Ctrl+V` was pressed. The wire shows the client's `key` envelopes followed by `clipboard_set`, and
another X client reading the selection back got `host-side paste text` — the text the host pasted,
served from the app's own display. Firefox's synthetic `Ctrl+V` fills no `paste` data, so no
`clipboard_set` went out and the read-back still showed the previous owner's text: that direction
is **not exercised** in Firefox by this rig.

### The CSP, and the page's own policy

The document came back under

```
default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self';
img-src 'self' data: blob:; frame-ancestors 'none';
require-trusted-types-for 'script'; trusted-types 'none'
```

and the policy holds when something tries to get past it: injecting a `<script>` the way markup
injection would arrive threw `TypeError: … This document requires 'TrustedScript' assignment`, and
an injected `<style>` was refused (`style-src 'self'`), leaving the page's colours untouched. Both
were console errors, and there were **no page errors at all** in either browser (2 console
messages, both of them these two refusals).

### The streamer's side: the token, an idle session, and acks

A wrong token in the page was refused (`#status = "closed: bye"`, no session id, and the streamer
logged `handshake refused reason="bad token"`); the token the recipe printed opened
`session session-1`. With the session open and nothing touched for five seconds, the client
received **0 messages** and sent **0** — an idle window sends nothing. The client's own acks are
on the wire (`frame_ack`, one per frame it drew), which is the ack side of the flow control: the
frames it did receive were the two the surfaces needed at the start.

## Defects and observations

### 1. Changing the cursor on the display ends the session

**What happens.** With the streamer serving, another X client changes the display's cursor
(`xsetroot -cursor_name crosshair`, or `hand2`). Within a second the streamer logs

```
ERROR appricot_streamer::session: display dead; session ended session=session-1
ERROR appricot_streamer: the session ended on a fault; exiting bound=Loopback(127.0.0.1:8391)
```

and leaves with status 3. In the page, `#status = "closed: bye"`; no `cursor_image` ever arrives,
only the `cursor_gone` from the start of the session; the host draws no cursor overlay
([chromium-cursor-step-ended-session.png](chromium-cursor-step-ended-session.png)).

**Reproduction.** Start the demo (README), connect a browser, then run
`/xtools/usr/bin/xsetroot -cursor_name crosshair` on its display. The pass does exactly this as
its last step, and it is last for this reason: the death cannot take the rest of a run with it.

**Reproduced** in both browsers' runs and in a container where no browser was attached at all, so
it is not about the session — while the X server itself is fine: in that same container, after the
streamer had exited, `xdpyinfo` on a fresh connection still answered, so the display was never
dead. **It is not deterministic**: one earlier run survived the same command and served a
`cursor_image` afterwards. The trigger is therefore not pinned to the cursor alone, and the
streamer's own report ("the display died") is not what happened.

**Why it matters for M2.** The cursor is an M2 criterion, and no cursor image reached the host in
any run of this pass: what was exercised is the failure, not the feature. A session image that
must show the app's cursor needs this fixed; a reproduction is above.

### 2. A Greek character needs a display whose keymap holds it

Measured, and it is not a defect: on the recipe's default `us` display, typing α in the browser
makes the client send the right keysym and the backend refuse it — by design, never pressing
another key for a keysym the keymap does not hold — with `input delivery failed … what="key"` in
the streamer's log and nothing at the app. The pass sets `setxkbmap us,gr` before the streamer
starts (the rig README shows where), and then α, € and ά all arrive. A session image meant to type
Greek needs a layout set the same way.

### 3. A browser that closes ends the demo run

By design ([protocol/v0.md §7](../protocol/v0.md#7-reattachment): one session per process, a 10 s
resume grace), and worth
knowing when reading the logs: when the browser closed, the streamer parked the session, tore it
down when the grace expired, and exited 0, and the recipe stopped the server with it. One browser
is one run of the recipe.

## What could not run, and why

- **Safari.** No macOS on this workstation, so the third desktop browser of the criterion is not
  run here. One line, as the task said, and it stays owed.
- **Greek, AltGr and dead keys in Firefox.** The rig cannot express them: Playwright's Firefox
  keyboard refuses the key names, and a synthetic DOM event would not be the browser's own input.
  Not run, not failed.
- **The host-to-app paste in Firefox.** A synthetic `Ctrl+V` produces no clipboard payload for the
  `paste` event there, so the client never sent `clipboard_set`. Not exercised.
- **The hostile fixture's three refusals, and the decoders' fuzz tests.** CI tests, by the M2
  criterion's own words; this pass did not re-run them.
- **Everything that needs the pilot application on a real device.** Equipment, deferred by name.

## What this means for M2

The browser half is recorded for two of the three browsers: the host's window behaviours, the
popups, input including the Greek cases, both clipboard directions, the strict CSP, and the
streamer's own contract through the page. It is **not** M2's exit: Safari is owed, the cursor
criterion ends in a defect rather than in a pass, the Firefox gaps above are real gaps in the
record, and the device half — the pilot application on a real device — is still owed. M2 stays
open, and `0.1.x` is what says so.
