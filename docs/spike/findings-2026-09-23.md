# Spike findings, 2026-09-23 and 24: the pilot application

The first runs of the M1 capture spike harness ([README.md](README.md)). Sections 1 to 7 are the
pilot application's first window, with no device connected, run by scripts; section 8 is one
run connected to a device, driven by a person in the browser; section 9, run the next day, is a
click on a covered window. What is still open, and where each item went when M1 closed, is at
the end ([What is still open](#what-is-still-open)).

**Method.** `just spike` in the `spike` container: Docker Desktop on a WSL2 kernel (6.18),
16 CPUs, 15.6 GiB; the Debian 12 spike image; Xvfb (X.Org 21.1.7) at 1400x900, depth 24; the
streamer and the tools as release builds; the recorder offering QOI. Scripts from
`scripts/spike/scenarios/` and knob files from `docker/spike/knobs/`, named per row. Two
consecutive releases of the pilot application gave the same figures to within 3 MiB; the tables
show the newer one. Mesa's llvmpipe is the only OpenGL there is. Figures from the earlier
**internal benchmark (September 2026)** are marked as such.

## 1. The window inventory

`startup.spike`, and a machine-local script that opens both combo boxes, holds the pointer
over a button for its tooltip, opens the settings menu, and presses the "new window" button.

| Window | Seen | X window | Properties |
|---|---|---|---|
| The main window | at start-up | toplevel, 1200x700 | `_NET_WM_WINDOW_TYPE_NORMAL`; `_MOTIF_WM_HINTS` flags 0x3, functions 0x3e, decorations 0x7e; no `WM_TRANSIENT_FOR`, no role |
| Combo-box lists (two) | on click | **none** | drawn inside the main window |
| A tooltip | after the pointer rests | **none** | drawn inside the main window |
| The settings menu | on click | **none** | drawn inside the main window |
| A second main window | on the "new window" button | toplevel, 1200x700, **from a second process** | as the first |

So on the login screen there is no override-redirect window at all: every popup is a Qt Quick
item inside its window. The 2026-09 benchmark said the same of the menus and the settings panel;
combo lists and tooltips are now logged too. The one new X window comes with a new process.

The window manager placed the second window at (200, 200), over the first: two 1200x700
windows cannot sit apart on a 1400x900 root, as
[architecture.md §4.2](../architecture.md#42-how-x11-maps-into-the-model) expected.

## 2. The scene graph and what it damages

The application's own log (`QSG_INFO=1`) says it renders Qt Quick through QRhi on **OpenGL**,
with a threaded render loop, on llvmpipe.

**Every repaint damages the whole window.** A GL swap presents the whole back buffer, so each
Damage event is 1200x700 = 840,000 px, whatever changed. Idle on the login screen, the text
cursor blinks twice a second, and that alone is two full-window repaints per second:

| `startup.spike`, one idle minute | OpenGL (baseline.env) | software scene graph (software-sg.env) |
|---|---:|---:|
| Damage events per second | 2.0 | 2.0 |
| Pixels per event | 840,000 (all full-window) | 6,900 (the cursor) |
| Frames sent | 120 | 120 |
| Tiles sent | 1,800 | 120 |
| Wire bytes, QOI | 8.1 MiB (about 135 KiB/s, 1.1 Mbit/s) | 2.8 KiB |
| Application CPU, idle | 2.1 % of a core | 0.1 % |
| Streamer CPU, idle | 1.4 % of a core | 0.4 % |

An idle session on the OpenGL path costs about 1.1 Mbit/s and 1.4 % of a core in the streamer,
for a cursor.

### The software scene graph fails its visual check

`QT_QUICK_BACKEND=software` (docker/spike/knobs/software-sg.env) halves the application's memory
(§3) and shrinks the damage to what changed. On the plain login screen its snapshot matches the
OpenGL one to all but 993 of 840,000 pixels: antialiasing of rounded corners and of translucent
text, invisible at 4x zoom. **But every popup loses its background.** The combo-box lists, the
settings menu and the tooltip draw their text over the controls beneath them, with no panel
behind it. This reproduces what the 2026-09 benchmark reported ("it broke a drop-down's
background"). The knob does not go into a profile as it is.

## 3. Memory and CPU, with the streamer in the session

`startup.spike`, the idle minute, one sample a second; MiB.

| | OpenGL | software scene graph | Internal benchmark, 2026-09, no streamer |
|---|---:|---:|---:|
| Application, RSS | 195 | 84 | 185-217 (about 193 on OpenGL, about 81 on software) |
| Xvfb, RSS | 81 | 80 | — |
| Streamer, RSS | 6.2 | 5.7 | not measured |
| Summed RSS, Xvfb + application | 276 | 165 | 286 (Debian 13) |
| Summed RSS, Xvfb + application + streamer | **282** | **171** | — |
| Display side, anon + shmem: Xvfb | 27.5 | 27.6 | about 36 (Debian 13) |
| Display side, anon + shmem: streamer | **2.0** | 1.6 | — |
| The container's cgroup, anon + shmem | 125 | 78 | — |

Anon + shmem per process is the proportional share (`Pss_Anon` + `Pss_Shmem` of
`smaps_rollup`); the cgroup row is the whole container, the spike's own tools (about 5 MiB)
included.

**The streamer costs about 6 MiB of RSS and 2 MiB of anonymous memory**, and 0.4-1.4 % of a
core at idle, depending on how much the application repaints. The Composite backing pixmap of
each window (3.4 MB for 1200x700) is in the X server's figure. Next to an application of
84-195 MiB, the streamer does not move the session's cost; the application's rendering path
does. This settles the open line of ADR-0004 ("The streamer's own memory and CPU come on top of
either, and have not been measured") for the login screen.

## 4. The codec

`bench.md` over every tile the recorder received (`startup.spike`, OpenGL, 1,965 tiles,
110 Mpx), each tile encoded five times, the fastest counted:

| | |
|---|---:|
| QOI size against RAW | 0.020 |
| QOI encode per 256x256 tile, p50 / p95 | 90 / 155 µs |
| One full 1200x700 frame (15 tiles) | about 1.4 ms, 68 KiB |
| Tiles where RAW was smaller | 0 |

On this application's flat, antialiased UI, the in-house QOI already takes a tile to 2 % of RAW,
fast enough that encoding is not the cost. The cost is what gets encoded (§2).

## 5. The keyboard check

`keyboard.spike` types four groups into the focused "connect to" field through the streamer's
XTEST input, the way the browser client sends them (docs/protocol/v0.md §8), once per X keyboard
layout (`--xkb`). What arrived, read off the snapshots:

| X layout | `abc ABC 123` | `αβγ ΑΒΓ ωσς` | `άέήίόύώ ϊΐ` (a dead-key accent, as the browser sends it) | `€@` (AltGr) |
|---|---|---|---|---|
| `us` (Xvfb's default) | all | nothing | nothing | `@` only |
| `gr` | digits and spaces only | all, final sigma included | nothing | `@` only |
| `us,gr` | all | nothing | nothing | `@` only |

The backend resolves a keysym against the first two columns of the core keymap only
(crates/appricot-x11/src/keymap.rs): the first group's unshifted and shifted levels. So one
layout works at a time, a second group is never reached, and a character that needs AltGr
(level 3) or exists on no key — every accented Greek vowel, `€` — is refused with
`KeysymUnavailable`, never typed as another key. The session survives each refusal.

M2 needs US and Greek with AltGr and dead keys. The backend has to deliver a keysym that is not
on the current keymap's first two levels. That is the next task on the X11 side, not a knob.

## 6. Capture under a covering window

With the second main window mapped over the first (§1), the first window's snapshot holds
none of the second's pixels, and its frames kept arriving: the "new window" button's tooltip,
drawn in the first window while it was covered, reached the host. The Composite redirect held
from start-up gives each window its own pixels, as the 2026-09 benchmark found.

## 7. Outside the display

The application's neighbour discovery finds nothing inside the container: its send to the IPv6
all-nodes multicast address fails, and nothing answers its broadcasts, which stay on the
container's bridge network (unverified: inferred from Docker's NAT, not traced). So its list of
neighbours stays empty. Connecting by address does not need discovery, and it works (§8).
Discovery is a layer-2 feature, and L2's egress design decides whether a session gets it.

## 8. Connected to a device

Demo mode (README.md, "Running"), `baseline.env`, OpenGL: a person logged in to a device on the
local network through the demo page, worked in the connected UI, then pressed the application's
"new window" button five times: in the connected window it opened a second connected window,
and after that it opened login windows. One run of about nine minutes; the phases below are cut from
its timestamps, since no scenario labels were set. Demo mode has no recorder, so there are no wire
figures and no snapshots; the person's browser was the visual check.

**Connecting by address works from the container; discovery does not** (§7). The device was
reached by its IP address through Docker Desktop's NAT.

**Every window of the connected UI is drawn inside the main window.** The connected session
turned the login window into the session window (its title changed; no new X window). Nothing
it opened while the person worked mapped an X window. Each press of "new window" started a
new process with one new 1200x700 toplevel (`_NET_WM_WINDOW_TYPE_NORMAL`, the same Motif hints
as §1), and no override-redirect window appeared in the whole run.

| Phase | Application processes | Application RSS / PSS / anon + shmem | Xvfb anon + shmem | Streamer RSS / anon | cgroup anon + shmem | Damage events/s (all full-window) | CPU %: application / streamer |
|---|---:|---:|---:|---:|---:|---:|---:|
| Login screen | 1 | 195 / 170 / 88 | 27.7 | 5.1 / 0.9 | 134 | 2.0 | 2.7 / 0.6 |
| Connected, one window | 1 | 274 / 249 / 164 | 27.7 | 7.2 / 3.0 | 225 | 5.4 | 21.8 / 3.6 |
| Six windows | 6 | 1,291 / 757 / 654 | 73.5 | 7.5 / 3.2 | 776 | 3.3 | 12.3 / 0.7 |

MiB, means over each phase; CPU is percent of one core.

- **A connected session costs about 90 MiB more than the login screen** (cgroup anon + shmem
  134 → 225 MiB), and the application's repaints rise to 5.4 full-window frames a second.
- **Each extra window costs about 110 MiB** (cgroup anon + shmem, 225 → 776 MiB for five), of
  which about 9 MiB is in the X server. Per process, RSS reads about 200 MiB but PSS about
  110 MiB: the processes share the executable's pages, so RSS nearly doubles the cost of a
  second window.
- **The streamer stays at about 7 MiB RSS** with six windows, and at 3.6 % of a core at the
  busiest phase.

A session's cost is therefore not a constant: the user opens windows, and each is a new
process. L2 has to cap it per session (memory, or processes), and a profile's footprint has to
be stated per window as well as per session.

## 9. A click on a covered window

Run on 2026-09-24, after the rest. A machine-local script pressed "new window" in the first
window, so the second one mapped at (200, 200) over it, then sent `FocusNotify` for the first
window and clicked its workspace combo box, whose place in the root the second window covered.
The streamer raised the first window before the press: the first window's snapshot shows the
combo box's list open, and the second window's snapshot did not change by one pixel. The click
reached the window it named, not the one on top at that point of the root.

## What is still open

M1 was closed on 2026-09-24 by the user's decision
([roadmap.md](../roadmap.md#m1-wire-spec-v0-and-the-x11-capture-spike)): S1 is the backend, with
ADR-0004 accepted. What the spike leaves open goes on as follows.

- **The keyboard** (§5): to M2, whose input criterion requires US and Greek, AltGr and dead keys.
- **The idle cost of the OpenGL path**, which the connected UI raises (§8): to M2, as a proposal.
  Two ways to cut it: a knob that keeps OpenGL but breaks nothing visible (none found yet), or
  a streamer that compares each damaged tile with the one it last sent and skips unchanged
  tiles. The second is a proposal, not a decision.
- **Who supervises Xvfb and the application, the streamer's uid, and a per-session cap on
  windows or memory** (§8): to M4, the L2 node.
- **S3**: not priced, by decision. S1 met every need these runs measured.
- **Wire figures and snapshots of the connected UI.** Demo mode has neither. A record-mode run
  needs the session to log in without a person: a persistent home for the application (so a
  saved connection survives the container) and a machine-local script that presses Connect.
  Worth a run when M2's streamer changes need a baseline.
